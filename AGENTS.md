# AGENTS.md — обязательные правила Map

## Приоритет

1. Прямое решение владельца в текущей задаче.
2. Этот файл.
3. Принятые записи `docs/DECISIONS.md`.
4. Остальная документация.

## Продукт

Map — личная нативная офлайн-программа владельца для его текущего Windows x64 ПК.

- Не превращать её в сайт, Electron/Tauri/WebView или обязательный облачный клиент.
- Без нового прямого запроса не готовить другой ПК, чистую Windows, VM/Sandbox, installer,
  updater, portable/release-пакет, подпись или публикацию. Обычная локальная Release-сборка и
  явно запрошенное переключение ярлыка на этом ПК не являются разрешением на распространение.
- Не копировать код, ассеты, фирменный стиль или закрытые данные Inkarnate. Использовать только
  собственные материалы и публично наблюдаемое поведение.

## Перед изменениями

Кратко прочитать `CODEX.md`, `docs/STATE_HANDOFF.md`, относящуюся к задаче спецификацию и
принятые решения. Зафиксировать branch, `HEAD` и существующие пользовательские изменения.
Перед созданием новой stage-ветки проверить `git log --all`: рабочий checkout может быть старше
последнего продуктового снимка.

## Как работать

- Делать только запрошенное, небольшими понятными изменениями.
- Не удалять, не сбрасывать и не присваивать себе существующие изменения владельца.
- Не добавлять зависимости, сервисы, аккаунты, секреты и инструменты без необходимости.
- Сохранять архитектурные инварианты: Core не зависит от UI/Skia; документ является источником
  истины; rendering не меняет документ; редактирование остаётся undoable; сохранение атомарное;
  основные сценарии работают без сети.
- Не создавать процессные prompt/review/evidence-файлы и не хранить generated artifacts, если
  владелец прямо их не запросил.
- Использовать только инструменты, реально доступные в текущей сессии. Codex получает эти правила
  напрямую; Claude Code — через короткий `CLAUDE.md`. Provider-specific команды и расширения не
  переносить между средами.

## Непрерывность продукта

- Новый функциональный этап начинается от последнего принятого продуктового `HEAD`, указанного в
  `docs/STATE_HANDOFF.md`, а не от случайно открытого или более удобного старого checkout.
- Отмена этапа отменяет только соответствующий scope. Полезный production-код
  предыдущих этапов не удаляется и не обходится без прямого решения владельца.
- Stages 12A–17 реализованы в линейной истории. Stage 17 разрешён отдельным поручением владельца;
  Stage 18 и далее не начинать автоматически. Следующее действие берётся из `docs/STATE_HANDOFF.md`.
- Если текущая папка содержит уборку на старом `HEAD`, её смысл переносится поверх последнего
  продуктового снимка; новые функции из более поздней линейной истории сохраняются.

## Минимальная проверка

- Изменён production-код или конфигурация сборки: один раз собрать `Map.slnx` в Release.
- Изменена конкретная логика с реальным риском регрессии: запустить только относящийся к ней
  test-project или фильтр. Полный набор тестов по умолчанию запрещён.
- Изменён UI или пользовательский сценарий: один короткий smoke в настоящем окне на текущем ПК.
- Документационные изменения не требуют build/tests.
- Не запускать повторно зелёную проверку без изменения входных данных.
- VM/чистая Windows/другой ПК, installer/release/portable, полный suite, coverage, mutation,
  benchmark, security scan, SBOM, pre-commit, DPI/accessibility matrix и независимая повторная
  приёмка выполняются только по отдельному прямому запросу владельца.

## Статусы и итоговый отчёт

Использовать статусы строго по смыслу:

- `FACT` — утверждение подтверждено для названного текущего снимка кодом, состоянием Git,
  выполненной проверкой или другим прямым доказательством; это не план и не предположение.
- `PARTIAL` — подтверждена только часть результата; рядом явно указать, что уже доказано и чего
  не хватает для полного утверждения.
- `PROPOSED` — предложение, план или оценка; это ещё не реализованный и не проверенный результат.
- `BLOCKED` — продолжение действительно невозможно из-за конкретного препятствия; указать само
  препятствие и что нужно для продолжения.
- При необходимости использовать `NOT CHECKED` для сознательно не выполненной проверки,
  `NOT CLAIMED` для результата, который отчёт сознательно не заявляет, `HISTORICAL` для факта
  старого названного снимка, `ASSUMPTION` для рабочего допущения и `REJECTED` для утверждения или
  результата, опровергнутого проверкой.

В отчёте кратко указать: что изменено, что реально проверено, что не проверялось и почему.
Каждый итоговый отчёт обязан заканчиваться разделом `## ИТОГИ`, написанным простым языком без
расчёта на программиста. В нём обязательно указать:

1. `Сделано:` что именно готово и что это даёт владельцу.
2. `Что дальше:` один понятный следующий шаг или честно написать, что обязательных действий нет.
3. `Реализация проекта: N%` — округлённую оценку готовности относительно текущего принятого scope
   и roadmap с одним коротким объяснением основания и неопределённости.

Процент является оценкой объёма, а не процентом тестов. Не считать готовыми `PARTIAL`, `PROPOSED`
или `BLOCKED` пункты и не создавать ложную точность. Любой будущий исполняемый prompt для Map
должен прямо требовать такой финальный раздел.

## Git

- Не переписывать историю и не выполнять reset/restore/stash пользовательских изменений.
- Commit, push, PR, tag, release и публикация — только по прямому запросу владельца.
- Локальный commit не требует pre-commit hook или отдельной review-сессии.
- GitHub remote, репозиторий, Project, issue и изменение scope токена являются внешними действиями
  и создаются только по прямому разрешению владельца. Текущая схема описана в
  `docs/GITHUB_PROJECTS.md`.
