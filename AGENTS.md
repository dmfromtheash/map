# AGENTS.md — обязательные правила проекта Map

Инструкции применяются ко всему репозиторию. При конфликте действует порядок:

1. Прямое решение владельца в текущей задаче.
2. Этот файл.
3. Принятые (`accepted`) записи `docs/DECISIONS.md`.
4. Утверждённая спецификация этапа.
5. Остальная документация.

## Назначение

Создаётся нативная офлайн-программа Windows для конструирования карт. Нельзя превращать её в сайт, веб-приложение, Electron/Tauri/WebView-оболочку или клиент обязательного облачного сервиса без нового решения владельца.

## Границы чистой реализации

- Изучать можно публичные материалы, публичный исходный код по зафиксированному commit и
  наблюдаемое пользователем поведение. Когда функция имеет зрелый публичный аналог, Codex должен
  прочитать относящиеся методы и тесты, чтобы понять алгоритм, структуры данных, крайние случаи и
  известные ошибки, а не полагаться только на README или придумывать решение вслепую.
- Разрешено использовать отдельные фрагменты публичного кода как материал для анализа и понимания.
  В Map пишется собственная реализация под наши domain/command/persistence/rendering контракты:
  запрещены перенос целой подсистемы, механический построчный перевод, сохранение узнаваемой
  структуры/комментариев/fixtures без отдельного решения о direct reuse. Для значимого reference
  фиксируются upstream, exact commit, прочитанные файлы, лицензия, извлечённые решения и собственные
  проверки. Direct reuse требует отдельного admission с attribution и removal plan.
- Запрещены скрейпинг закрытого интерфейса, извлечение внутренних сетевых моделей, декомпиляция,
  обход ограничений, а также копирование исходного кода, ассетов, названий наборов, фирменной
  графики или визуального оформления Inkarnate.
- Реализация должна иметь собственные названия, дизайн-токены, иконки и ассеты.
- Материал с неясной лицензией считать запрещённым до письменной фиксации происхождения.

## Как работать

- Перед изменениями прочитать `CODEX.md`, `docs/00_START_HERE.md`, `docs/STATE_HANDOFF.md`, текущую запись этапа в дорожной карте и относящиеся к ней решения.
- Основной исполнитель — Codex на модели `gpt-5.6-sol`. Для реализации использовать reasoning `high`; для архитектурных, security- и независимых acceptance-проходов — `xhigh`. Повышать до `max` только для действительно трудной локальной задачи, а не по умолчанию.
- Рабочая единица — один целостный вертикальный этап дорожной карты: пользовательский результат, доменная логика, persistence/rendering/UI по необходимости, тесты, реальный сценарий и evidence. Не дробить обычный этап на серию микропромтов, но и не смешивать соседние этапы с разными acceptance-gates.
- Не расширять задачу. Найденную соседнюю проблему записать в отчёт, но не исправлять без разрешения.
- Предпочитать минимальные, понятные и обратимые изменения.
- Не менять архитектурные границы, формат проекта и целевые бюджеты скрытно. Для этого нужна запись в `docs/DECISIONS.md` со статусом `proposed` и решение владельца.
- Не добавлять пакеты «на всякий случай». Для каждой новой зависимости нужны назначение, лицензия, актуальность, альтернатива и причина отказа от стандартной библиотеки.
- Не добавлять секреты. Если когда-либо появится интеграция, использовать локальное хранилище пользователя и `.env.example`, но не `.env` в репозитории.
- Не повторять одно и то же ограничение в нескольких формулировках внутри этапного промта. Один раз задать outcome, scope, полномочия, критерии и условия остановки. Внутри разрешённого scope Codex действует самостоятельно; спрашивает владельца только при новом продуктовом решении, внешнем/необратимом действии, расходах, публикации или существенном расширении scope.
- Инструменты выбираются по риску этапа. Каждый промт содержит матрицу `риск -> инструмент -> доказательство -> причина пропуска`; запускать весь каталог инструментов без проверяемой цели не нужно.
- До изменений каждый промт фиксирует **verification budget и stop rules**. На неизменившемся снимке один и тот же успешно пройденный gate не повторяется «для уверенности»; повтор разрешён только после относящегося изменения или для заранее объявленного flake/timing/concurrency-риска. Полный бюджет и пределы повторов заданы один раз в `docs/11_CODEX_VERIFICATION_PROTOCOL.md` и обязательны для всех новых, повторно используемых и review-fix prompt'ов.
- Изучение upstream-кода само по себе не запускает сборку, тесты, security scan или benchmark всего
  upstream/Map. Читать нужно минимальный набор файлов, отвечающий на конкретный вопрос; собирать или
  исполнять чужой checkout — только по отдельному risk trigger. Docs-only изменение не требует
  .NET build/test/native gates: достаточно относящихся document, link/prompt и Git checks.

## Архитектурные инварианты

- Доменная модель документа не зависит от Avalonia и Skia.
- UI не является источником истины для карты.
- Рендеринг не изменяет документ.
- Сохранение атомарное; миграция не перезаписывает единственную копию старого файла.
- Каждая редактирующая операция проходит через команду, пригодную для undo/redo и тестирования.
- Идентификаторы документа, слоёв, объектов и ассетов стабильны.
- Сетевой доступ не является условием запуска, сохранения, редактирования или экспорта.

## Проверка

Проверки должны быть достаточными для риска, но конечными. Нельзя превращать этап в цикл повторного запуска уже зелёных команд. Если обязательное доказательство не получено в пределах бюджета, результат фиксируется как `PARTIAL`/`BLOCKED` с причиной и следующей диагностикой, а не маскируется дополнительными одинаковыми прогонами.

Для каждого этапа отдельно указать:

- что проверено автоматически;
- что проверено вручную в настоящем окне приложения;
- что не проверено и почему;
- какие файлы и сценарии затронуты;
- известные риски и точную следующую задачу.

Нельзя писать «готово», если не выполнен хотя бы один обязательный критерий приёмки. Использовать статусы `FACT`, `PARTIAL`, `PROPOSED`, `BLOCKED`.

## Работа с Git

- Не переписывать историю и не удалять пользовательские изменения.
- Не выполнять публикацию, push, создание PR или релиза без прямого запроса владельца.
- Коммит, когда он разрешён, должен соответствовать одному этапу или одной исправляемой проблеме.
- Не коммитить рабочий срез прямо в `main`; использовать `stage/NN-*` или `fix/*`.
- Перед коммитом обязателен установленный `pre-commit` hook и свежий self-check среза.
- После коммита задача реализации Codex останавливается. Свежая задача/сессия Codex независимо проверяет точный `BASE..HEAD`, рабочее дерево, число и список файлов, ссылки между проектами, реальные артефакты и пользовательский сценарий. Самопроверка в том же контексте не называется независимой.
- Найденные дефекты исправляются новым отдельным коммитом; `--amend`, rebase и скрытое переписывание проверенного снимка запрещены.
- Полный порядок и уровни проверки определены в `docs/11_CODEX_VERIFICATION_PROTOCOL.md`.
