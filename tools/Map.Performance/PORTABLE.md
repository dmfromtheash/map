# Переносимые заготовки ассетов

Обычный `StampDerivedAssetStore` только читает `<каталог>/derived/v1/<sha>.mapderived`.
Отсутствующие, устаревшие или повреждённые данные восстанавливаются в рабочем потоке;
обычный рендер не записывает portable-файлы в библиотеку. Машинный кэш остаётся в профиле.

Явная подготовка (БЕЗ ОКНА, операция записи в указанные каталоги):

```powershell
dotnet run --project tools/Map.Performance -c Release --no-build -- --profile derived-build --catalogs C:\MyLibrary\catalog --dry-run --output C:\Checks\derived-plan.json
dotnet run --project tools/Map.Performance -c Release --no-build -- --profile derived-build --catalogs C:\MyLibrary\catalog --output C:\Checks\derived-result.json
```

После подготовки записывается также `derived/v1/overview-colors.bin`: одна переносимая палитра
по SHA (68 байт на запись + 48 байт на файл), с версией, SHA256 всего содержимого и отпечатком
относительных путей/длин оригинала и рабочей ступени. Она нужна именно **пустому машинному кэшу**:
для обзорных точек больше не требуется открывать отдельный заголовок каждого ассета. Заголовки и
точные mip читаются по запросам пикселей; видимые запросы обходят очередь остальных цветов.
В активную палитру принимаются только запрошенные ассеты. Сам файл палитры читается один
раз для каждого запрошенного каталога; источники неиспользуемых записей при этом не обходятся.

Уже готовую библиотеку можно снабдить палитрой без пересборки изображений и чтения их пикселей:

```powershell
dotnet run --project tools/Map.Performance -c Release --no-build -- --profile derived-colors --catalogs C:\MyLibrary\catalog --dry-run --output C:\Checks\colors-plan.json
dotnet run --project tools/Map.Performance -c Release --no-build -- --profile derived-colors --catalogs C:\MyLibrary\catalog --output C:\Checks\colors-result.json
```

`colorEntries` — число пригодных записей; `images - colorEntries` — не вошедшие в палитру
(нет/повреждён portable или не совпали источники). `io.sourcePreparations` и
`io.sourceVerifications` этого режима равны нулю: только заголовки и stat, без декодирования и
хеширования оригиналов. `--dry-run` не меняет библиотеку. Пустая/повреждённая палитра означает
обычный путь через заголовки, а не отказ открыть карту. Старые версии программы игнорируют её;
формат `.mapproj` и `.mapderived` не менялся. Обычный рендер библиотеку по-прежнему не записывает.

Цвет из переносимой палитры предварительный по той же политике, что portable-header: SHA
оригинала/ступеней проверяется фоном, когда очередь видимых пикселей освободилась и 250 мс нет
новых запросов. Холст также сообщает, закончилась ли растеризация вида: пустая очередь картинок
не означает, что миллион объектов уже собран в обзор. Пока вид дорисовывается, проверки оригиналов
ждут. Изменившийся источник, ошибочный manifest или исчезнувший portable инвалидируют
цвет; в машинную палитру попадают только подтверждённые цвета. Точные пиксели каждого mip всегда
проверяются по прежнему SHA. Manifest одного открытого файла кэшируется по его длине/mtime
(до 1024 записей), без изменения выбора mip или правил рисования.

Headless-сторожа: `ColdStart100kIndexedTests`, `ColdStartMillionIndexedTests` и соответствующие
`LegacyTests` без переносимой палитры (100 тысяч/миллион объектов, 3072 записи, 3000
размещённых SHA, новый пустой local-derived в каждом случае) и `PortableColorIndexTests`
(целостность, перенос, источники, закрытие, dry-run). Для fit требуется полное покрытие карты,
нулевые unresolved/pending и не более 60 заголовков при наличии палитры: только каждый 50-й SHA
имеет крупные штампы, 3000/gcd(3000, 50)=60. Для приближения требуются четыре точные видимые
плитки без подмен/пробелов либо их готовый слой; необязательная грубая заготовка учитывается
отдельно. CPU-пределы теста: 6 с до полного fit (>3× измеренного холодного fit после правки на
контрольном Mac) и 10 с до резкого вида; это не Windows/GPU FPS.
Каждый из четырёх классов можно запускать runner-ом в отдельном процессе: тогда предыдущий
сценарий не прогревает JIT и статическое состояние рендера. `ColdStartPipelineTests` отдельно
проверяет, что видимые заголовки обгоняют очередь фоновой палитры.
Для строгого холодного процесса передать `MAP_COLDSTART_LIBRARY_ROOT`: заранее созданную отдельным
процессом библиотеку из 3072 fixture-записей (для `IndexedTests` с палитрой, для `LegacyTests` без неё).
Тест читает её, не создаёт и не удаляет. Локальный derived по-прежнему новый в каждом запуске.

Запускать запись только для каталогов, которые разрешено изменять. В задаче USER
`D:\MapLibrary` остаётся источником чтения; эти команды туда не запускались.
Файл содержит цвет обзора, вспомогательную маску32×32 и точные premultiplied mip
до1024px; маска пока не участвует в отсечении объектов. Заголовок и блоки проверяются
по версии, границам и SHA256. Пути источников относительные. Первое доверие на машине
требует SHA оригинала и всех ступеней; подтверждение размера/mtime хранится только
в машинном кэше и входит в его дисковый лимит. Изменение mtime повторяет проверку байтов.
Повреждённый portable исключается до изменения файла, запросы восстанавливают локальный
кэш. Запись идёт во временный файл с атомарным переименованием. Явный builder требует
отдельного экземпляра стора, не обслуживающего холст.

ЖИВОЙ A/B использует обычный профиль `native-million-assets`:

```powershell
$env:MAP_DRIVE_LIBRARY_ROOTS='D:\MapLibrary'
$env:MAP_PERF_PORTABLE_FIXTURE='plain' # второй вариант: portable
$env:MAP_MEASURE_GPU_FLUSH='1'
dotnet run --project tools/Map.Performance -c Release --no-build -- --profile native-million-assets --object-count 100 --output C:\Checks\portable-live.json
```

Режим fixture импортирует первые100 SHA-сортированных исходников владельца в отдельный
временный каталог профиля. `portable` явно готовит заготовки только там. В обоих режимах
измеряемый машинный кэш сначала пуст; подготовка fixture идёт до открытия измеряемого
редактора и записывается отдельно. Маршрут, seed и картинки одинаковы. Профиль после
проверки удаляется; окно/GPU и итоговые пиксели проверяются отдельно от тестов reader/writer.
Импорт прогревает файловый кэш Windows: этот A/B не является проверкой холодного диска ОС.
