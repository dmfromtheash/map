# CODEX.md — рабочий вход Codex в Map

`AGENTS.md` — единственный обязательный репозиторный источник правил, который Codex читает автоматически. Этот файл поясняет рабочий профиль проекта и не переопределяет `AGENTS.md`.

## Профиль исполнения

- Модель: `gpt-5.6-sol`.
- Reasoning: `high` для реализации полного этапа; `xhigh` для архитектурной проверки, security-аудита и независимой приёмки. `max` — только когда конкретная сложность это оправдывает.
- Среда: нативный Windows/.NET/Avalonia/Skia проект. Web/Electron/Tauri/WebView не являются допустимой заменой.
- Автономность: read-only исследование и обратимые изменения внутри явно заданного scope выполняются без повторного запроса. Остановиться нужно перед новым продуктовым решением, внешней публикацией/сообщением, расходами, необратимым действием или существенным расширением scope.

## Перед реализацией

Прочитай полностью и в этом порядке:

1. `AGENTS.md`;
2. `docs/00_START_HERE.md`;
3. `docs/STATE_HANDOFF.md`;
4. текущий этап в `docs/06_DEVELOPMENT_ROADMAP.md`;
5. относящиеся к этапу accepted-записи `docs/DECISIONS.md`;
6. конкретный контракт из `docs/prompts/`;
7. `docs/07_CODEX_RUNBOOK.md` и `docs/11_CODEX_VERIFICATION_PROTOCOL.md`.

До кода зафиксируй фактический branch/HEAD/worktree, текущие пользовательские изменения, границы этапа, acceptance-gates и короткий план внутренних checkpoint'ов. Существующий dirty worktree не очищать и не присваивать себе.

## Размер задания

Один prompt должен закрывать один цельный вертикальный этап или крупный однородный блок этапа, пригодный для пользовательской приёмки. Внутри него могут быть доменная модель, команды undo/redo, persistence, rendering, presentation, UI, тесты и evidence — если всё это нужно одному результату.

Не объединяй соседние roadmap-этапы только ради большого diff. Срочный fix после независимого review остаётся отдельным узким заданием, потому что его цель — доказать исправление конкретного дефекта.

## Метод работы

1. Сформулируй наблюдаемый outcome, а не перечень файлов.
2. Построй матрицу `риск -> инструмент -> ожидаемое доказательство -> условие пропуска`.
3. Для поведения сначала получи failing test/воспроизведение; для документационной миграции — failing inventory/checklist.
4. Вноси изменения по внутренним checkpoint'ам и проверяй каждый checkpoint, но не останавливай этап после первого зелёного теста.
5. Выполни полный self-check этапа, прочитай вывод и проверь артефакты как данные.
6. Коммит создавай только если текущий prompt прямо это разрешает. После коммита сообщи `BASE`/`HEAD` и остановись для свежего независимого Codex-review.

До первого запуска проверок зафиксируй конечный `verification budget` из prompt. Успешный gate на том же снимке выполняется один раз; повтор допустим только после релевантного изменения или при заранее названном flake/timing/concurrency-риске. При исчерпании бюджета останови повтор и честно выдай `PARTIAL`/`BLOCKED` по правилам `docs/11_CODEX_VERIFICATION_PROTOCOL.md`.

## UI и canvas

Для видимого изменения недостаточно существования screenshot:

1. запусти настоящий Release EXE и воспроизведи точное состояние;
2. сохрани пронумерованные PNG и сценарий в `artifacts/`;
3. открой каждый PNG в vision-контексте и письменно проверь hierarchy, clipping, overlap, alignment, focus, контраст, пустые состояния и canvas-result;
4. для сравнимых состояний используй `scripts/compare-ui-screenshots.ps1`, normalized RMSE и diff PNG;
5. стандартные controls проверь через project-owned UI Automation driver и, когда требуется, Accessibility Insights;
6. golden/reference нельзя автоматически перезаписывать тем же прогоном, который изменил rendering.

## Инструменты

Используй только инструменты, относящиеся к риску этапа. Базовый .NET/Git/pre-commit контур обязателен перед разрешённым коммитом. Coverage, Stryker, diagnostics, Avalonia Headless, UIA/Appium, ImageMagick, Accessibility Insights, browser research и security scan включаются по условиям из `docs/11_CODEX_VERIFICATION_PROTOCOL.md`.

Не устанавливай сторонний desktop-control MCP и не подключай плагин только потому, что он доступен. Browser/GitHub/connectors не получают право на внешнюю запись без прямого запроса владельца.

Финальный отчёт — строго по `docs/07_CODEX_RUNBOOK.md`: `FACT`, `PARTIAL`, `PROPOSED`, `BLOCKED`, реальные команды/сценарии, затронутые файлы, пропущенные проверки с причиной, риски и точный следующий этап.
