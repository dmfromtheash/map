# Резервный блок отрисовки («запасное колесо») — исследование и проект

Поручение владельца 14.11: отдельный вспомогательный блок на случай слабой графики, исчерпанной графики и отсутствия
графики; работает **в связке** с ядром DEC-111 (бюджет кадра, планировщик, регулятор качества, память), а не поверх и
не вместо. Два независимых исследования: Claude (агент, 25 источников) и Sol 6.1 high (127 позиций поиска); полные
отчёты — журнал 14.11. Метки: КОД — подтверждено исходником; АВТОРЫ — документация; PROPOSED — предложение.

## 1. Что подтверждено (обоими исследованиями)
- **Avalonia 12.1.1 не умеет переключать GPU ↔ Software во время работы** (КОД): режим выбирается один раз при старте
  (`Win32PlatformOptions.RenderingMode` = `[AngleEgl, Software]`, `Win32GlManager.InitializeCore`), один Compositor на
  процесс. При потере устройства Avalonia пересоздаёт контекст **того же** провайдера (новое D3D11-устройство), на
  Software не спускается. Без ANGLE программа уже сама стартует в Software. WARP (программный D3D11) выбирается при
  старте через выбор адаптера / атрибут ANGLE `EGL_PLATFORM_ANGLE_DEVICE_TYPE_D3D_WARP_ANGLE`.
- **Наша отрисовка может рисовать в CPU-поверхность и класть результат на GPU-холст** — Map так уже делает для
  детальных плиток (`SceneRenderer.DetailRaster.cs`). В Software сейчас выключены кадр камеры, уточнение рельефа, атласы.
- **Образцы:** Chromium — блок-лист по возможностям, лестница HARDWARE → SwiftShader → программная композиция после
  3 падений GPU-процесса (прощение 1 падения / 5 мин), обратно в сессии не поднимается; потоков растра — половина ядер,
  1–4; приоритеты плиток NOW/SOON/EVENTUALLY (КОД). Firefox — WebRender → «CPU рисует, GPU складывает» (SW-WR + D3D11)
  → чистый SW-WR; стабильный GPU-процесс сначала перезапускает, лимит сбросов 10 (КОД). Unity Adaptive Performance —
  отдельно упор CPU / GPU / заливка, вход строже выхода (АВТОРЫ; код только для чтения). Unreal — запас 10 %, порог
  изменения 2 %, «паника» после N просроченных кадров подряд (АВТОРЫ).

## 2. Что блок делает (по эффекту и цене для Map)
1. **Меньше загрузок текстур за кадр** в жесте и при правках (начато: лимит приёма mip 8/2 МиБ, `d81db90`).
2. **Дольше держать кадр камеры** + CPU-версия этого кэша (сейчас в Software кадр камеры выключен).
3. **Пониженное разрешение сцены во время жеста** (точный кадр после остановки) — работает и на CPU.
4. **CPU-плитки сцены + GPU-композиция** («CPU рисует, GPU складывает», как Firefox) — на базе существующих
   детальных плиток, общий пул потоков (половина ядер, 1–4, ниже приоритет UI).
5. Проще эффекты в жесте (тени, размытие, свет).
6. **Ритм кадра:** начало кадра сразу после такта (измерение у Astra; `LowLatencyDxgiSwapChain` дал задержку ~28 мс
   против ~16 мс, по умолчанию не включать).
7. **Полный Software** — только как аварийный путь: при старте (нет ANGLE / плохой драйвер / после аварии GPU) или
   контролируемым перезапуском с восстановлением сессии; во время работы — нет готового механизма Avalonia.

## 3. Архитектура в связке с ядром DEC-111 (PROPOSED)
- **Один план кадра `FramePlan`** утверждает общий координатор (регулятор качества): разрешение сцены, лимит приёма
  картинок, политика кадра камеры, конкурентность фона, требования к точности. План известен **до**
  `StampImages.BeginFrame()`. Регулятор решает, *что* рисовать; резервный блок — *кто и как часто* рисует. Один
  владелец у каждой «ручки», одна ручка за период — чтобы два регулятора не боролись.
- Компоненты: `GraphicsProfileProbe` (адаптер, драйвер, WARP/VM/RDP, проба ≤ 1–2 с на ассетах владельца, профиль в
  локальных настройках), `RenderHealthMonitor` (общий датчик: время CPU/GPU, доля интервалов > 1,5·T, переполнение
  кольца GPU-таймера = рост очереди, память VRAM `QueryVideoMemoryInfo`, потеря устройства), `ReserveController`
  (чистая логика состояний без Win32), `CpuTileAssist`, `SceneSurfacePresenter` (пониженное разрешение, готовые
  изображения, полноразмерные элементы редактора), `GraphicsRecoveryCoordinator` (поколение ресурсов, ограниченные
  повторы, аварийный Software). Win32/DXGI — только в `Map.App`; Core без зависимостей от графики.
- **Состояния:** Probing → Normal ↔ Assisted (причины независимы: WeakProfile, GpuCost, UploadPressure, MemoryPressure,
  Pacing, DeviceFailure, UnknownTelemetry) → Recovering → Software → RecoveryProbe.
- **Пороги (стартовые, проверить замером):** GPU p95 > 0,75·T два окна по ~1 с → помощь; < 0,55·T несколько секунд →
  снятие; пропуски > 5 % в жесте → помощь, < 1 % за ~10 с → снятие; VRAM > 0,90 бюджета → стоп предзагрузке,
  < 0,75 → снятие. Минимум 3–5 с в ступени, ухудшение быстрее улучшения, повторный вход с удвоением задержки 5 → 60 с,
  после потери устройства — длинная пауза.
- **Проверка:** переменные `MAP_RESERVE_*` для принудительных режимов «слабая / исчерпана / нет»; «грузчик» GPU;
  PresentMon на HD 630; Software при старте; пиксели точного кадра не меняются (кадры жеста — по DEC-112).

## 4. Порядок
1. Наблюдение и единое решение (`FramePlan`, достоверный датчик GPU — текущий `GpuFrameTimer` ловит ~0,5 мс из ~10:
   переделать на охват всего кадра).
2. Помощь работающей графике: загрузки, кадр камеры, пониженное разрешение жеста, CPU-плитки.
3. Ритм кадра — только после доказанного эффекта.
4. Аварийный Software при старте и после аварии GPU; восстановление сессии; затем безопасный возврат GPU.

## 5. Решения владельца (нужны до пунктов 3–4)
- Может ли блок при следующем старте сам включать Software/WARP после аварии GPU?
- Допустим ли в жесте упрощённый формат кадра (8888 вместо F16) — пиксели движения не равны точным (DEC-112)?
- Можно ли на ноутбуке USER проверять сброс GPU (`dxcap -forcetdr` сбрасывает графику всей машины)?
