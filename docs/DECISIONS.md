# Журнал решений

Записи не редактируются задним числом. Новое решение либо принимает предложенное, либо помечает старое как `superseded` ссылкой на новый ID.

## DEC-001 — Нативная офлайн-программа

- **Статус:** `accepted`
- **Принято владельцем:** 2026-08-25
- **Дата:** 2026-08-25
- **Решение:** основной продукт — нативное Windows-приложение. Запуск, редактирование, сохранение и экспорт не требуют браузера, локального веб-сервера или интернета.
- **Причина:** прямое требование владельца.
- **Следствия:** Electron, Tauri, WebView, PWA и обязательный cloud backend не используются.

## DEC-002 — Технологический стек

- **Статус:** `accepted`
- **Принято владельцем:** 2026-08-25
- **Дата:** 2026-08-25
- **Решение:** C# 14 / .NET 10 LTS, Avalonia 12.1, прямой Skia-рендеринг сложного холста, CommunityToolkit.Mvvm для UI-состояния.
- **Причина:** нативное окно Windows без Chromium, MIT-лицензии, быстрый цикл для Opus, доступ к аппаратному и программному рендерингу, нормальная упаковка `.exe`.
- **Альтернативы:** Qt 6/C++ сильнее как зрелый scene framework, но повышает сложность и лицензионную нагрузку; Godot удобен для 2D, но хуже подходит к доступному document-centric desktop UI.
- **Ворота:** подтвердить spike с 10 000 объектов, пером, маской и offscreen export до принятия.

## DEC-009 — Очень большие карты, deep zoom и 16K+ являются архитектурным требованием

- **Статус:** `accepted`
- **Принято владельцем:** 2026-08-25
- **Дата:** 2026-08-25
- **Решение:** продукт не ограничивается типовой 4K/8K картой. Движок обязан поддерживать очень
  большой логический canvas, сильное приближение с сохранением доступной исходной детализации,
  16K export и export больше 16K тайлами/регионами без создания единого full-canvas bitmap.
- **Архитектурные следствия:** spatial culling, tiled raster storage, mip/LOD, bounded RAM/VRAM
  caches, фоновая подгрузка видимых данных, один scene evaluator для viewport/preview/export и
  отсутствие операций, стоимость которых скрытно пропорциональна площади всей карты.
- **Честная граница:** zoom не создаёт деталей сверх векторной геометрии или исходного разрешения
  ассета; UI должен показывать качество/LOD, а не обещать несуществующую детализацию.
- **Ворота:** минимальные измеримые профили фиксируются в roadmap и могут быть повышены только по
  фактическим benchmark; снижать их скрытно нельзя.

## DEC-010 — Функциональный паритет панели объекта и сеток

- **Статус:** `accepted`
- **Принято владельцем:** 2026-08-26
- **Дата:** 2026-08-26
- **Решение:** Map должен покрывать наблюдаемые инструменты выделенного stamp: replace asset,
  scale/rotation/sublayer, оба flip, opacity, shadow, blend, blur и Hue/Saturation/Brightness/
  Contrast; Shape получает прямое редактирование fill/stroke и общих эффектов. Grid panel должен
  открыть square, diagonal diamond, hex-flat и hex-pointy presets и все уже существующие точные
  параметры сетки.
- **Граница:** паритет относится к функции и результату. Названия, компоновка, tokens, icons,
  assets и visual language остаются собственными согласно DEC-003.
- **Gate:** поле в модели или renderer не считается готовой функцией без доступного control,
  фактического значения, одной undoable-команды, save/reopen и preview/export проверки.
- **Доказательная матрица:** `docs/research/OBJECT_AND_GRID_PARITY.md`.

## DEC-011 — Изометрические квадраты являются отдельной геометрией сетки

- **Статус:** `accepted`
- **Принято владельцем:** 2026-08-26
- **Дата:** 2026-08-26
- **Решение:** наблюдаемый preset Isometric Squares реализуется отдельной topology с собственными
  render, snap и fixtures. Его нельзя подменять квадратной сеткой, повёрнутой на 45°.
- **Причина:** прямое требование владельца о разнообразии сеток и проверка видимого результата в
  его тестовой карте 26.08.2026.
- **Следствия:** пункт DEC-010 о diagonal diamond как достаточном четвёртом preset superseded;
  остальная часть DEC-010 сохраняет силу. Изменение file kind и migration выполняются отдельным
  вертикальным срезом, не скрытно внутри UI.
- **Доказательство:** `docs/research/INKARNATE_ACCOUNT_WALKTHROUGH_20260826.md`.

## DEC-012 — Совместимые горячие клавиши являются default-профилем

- **Статус:** `accepted`
- **Принято владельцем:** 2026-08-26
- **Дата:** 2026-08-26
- **Решение:** Map использует наблюдаемый keyboard profile как default там, где соответствующая
  функция существует: глобальные команды, tool keys, selection transforms и контекстные
  Brush/Mask/Text действия. Клавиша без работающей команды не считается реализованной.
- **Причина:** прямое требование владельца сохранить привычную клавиатурную механику.
- **Граница:** собственные русские названия и UI сохраняются; редактируемые bindings остаются
  запланированным улучшением. Multi-selection, stamp sets и font catalog получают сочетания только
  вместе с реальной доменной функцией и undo/save/reopen gate.
- **Доказательство:** полный наблюдаемый список в
  `docs/research/INKARNATE_ACCOUNT_WALKTHROUGH_20260826.md`.

## DEC-013 — Каталог развивается как локальная Library, а не Marketplace

- **Статус:** `accepted`
- **Принято владельцем:** 2026-08-26
- **Дата:** 2026-08-26
- **Решение:** Map получает фундамент локального каталога с собственными collections,
  breadcrumbs, search, sort, group, filters, recent/favorite и virtualized thumbnail grid.
  Каталог работает полностью офлайн с пользовательскими и будущими собственными ассетами.
- **Граница:** аккаунты, магазин, публикация, cloud sync, чужие названия разделов, visual language
  и материалы не переносятся. Private imports пользователя не становятся частью starter pack.
- **Миграция:** существующий плоский каталог должен перейти на версионированную schema без потери
  SHA-256, linked/embedded mode, provenance, tags, pack и favorite; запись остаётся атомарной.
- **Gate:** 10 000 логических карточек открываются/фильтруются metadata-only, видимые thumbnails
  загружаются bounded cache, а keyboard/UIA/high-DPI сценарий проходит в настоящем окне.
- **Доказательство:** `docs/research/ASSET_CATALOG_AND_VARIANT_SETS.md`.

## DEC-014 — Один логический ассет может содержать много вариантов

- **Статус:** `accepted`
- **Принято владельцем:** 2026-08-26
- **Дата:** 2026-08-26
- **Решение:** каталог разделяет immutable content по SHA-256, стабильный `AssetVariant` и
  логический `AssetSet` с упорядоченными variants, cover и set-level metadata/favorite. Одиночный
  импорт является singleton set; множественный импорт может создать set из десятков вариантов.
- **Размещение:** tool state хранит выбранный variant, manual previous/next и toggle случайного
  выбора после размещения. Массовый gesture сначала разрешает все SHA/positions/random values,
  затем одной command добавляет готовые объекты; renderer никогда не reroll-ит вариант.
- **Формат проекта:** первый foundation-срез не меняет schema `.mapproj`. Карта хранит конкретный
  SHA каждого размещённого варианта и нужные `MapAssetReference`, поэтому reopen/undo/export не
  зависят от локального set. При доступном каталоге set находится обратно по SHA.
- **Gate:** миграция старого каталога, fixed/manual/random set placement, Area/Density scatter,
  undo/redo и save/reopen доказаны тестами на собственном много-вариантном diagnostic set.
- **Доказательство:** `docs/research/ASSET_CATALOG_AND_VARIANT_SETS.md`.

## DEC-015 — Бюджеты чтения локального контента и безопасные linked fallback

- **Статус:** `accepted`
- **Принято владельцем:** 2026-08-28, владелец прямо делегировал Codex завершение Stage 10D,
  исправления и оставшиеся технические решения в пределах текущего среза.
- **Дата:** 2026-08-28
- **Решение по linked paths:** `.mapproj` сохраняет только синтаксически относительный путь без
  NUL, `:`, drive/root/UNC/device namespace и пустых сегментов. Сегменты `.`/`..` сохраняются для
  совместимости старых относительных ссылок, но fallback автоматически открывается только когда
  канонический результат остаётся внутри папки проекта и цепочка не содержит reparse points.
  Внешний linked import сохраняет catalog/content identity без небезопасного файлового fallback;
  при недоступном каталоге результат — явный placeholder, а не произвольный local-file probe.
- **Решение по изображениям:** максимум 64 MiB encoded, 32 768 по каждой оси, 32 MiPixels и
  128 MiB расчётного RGBA на одно изображение. Production Skia cache — 64 элемента / 256 MiB
  conservative resident weight (`encoded + decoded`), Library cover cache — 96 элементов /
  64 MiB; место освобождается до нативного decode. Optional fallback thumbnail имеет отдельный
  предел 8 MiB encoded, 2048 по оси и 4 MiPixels и принимается только после полного decode. SHA,
  metadata и decode/embedding относятся к одним прочитанным байтам.
- **Решение по `.mapproj`:** 16 384 entries; JSON entry 32 MiB, tile 256 KiB, asset 64 MiB,
  preview 8 MiB; aggregate assets 256 MiB, tiles 256 MiB, JSON 64 MiB, всего 512 MiB. Compression
  ratio 1000 применяется ко всем entries с additive slack 1 MiB. Preview ограничен 8192 по оси
  и 16 MiPixels до UI decode. До `JsonSerializer` streaming semantic pass ограничивает известные
  materialized collections: 4096 layers, 100 000 scene/composition objects, 10 000 notes,
  16 384 assets, 500 000 vector nodes и 1 MiB UTF-8 на одну строку; остальные DTO-коллекции и
  общий token count также bounded. Это предотвращает object amplification внутри допустимого
  32 MiB JSON entry.
- **Совместимость v1:** номер схемы не меняется, потому что структура данных не изменилась.
  Более крупный старый v1-файл может не войти в текущий интерактивный memory envelope; это
  возвращается как `MapProjectResourceLimitException` («файл не изменён»), а не объявляется
  повреждением. Скрыто ослаблять лимиты или выдавать resource-limit за corruption запрещено.
- **Причина:** локальный/offline файл всё равно является внешней границей данных. Предыдущие
  пределы 512 MiB на один asset и 2 GiB на container допускали несколько полных копий payload и
  нативные декодеры вне измеримого рабочего бюджета.
- **Историческое доказательство:** review и generated test-артефакты существовали в срезе
  Stage 10D; локальные копии удалены 2026-08-30 как неисполняемая обвязка, история сохранена в Git.

## DEC-016 — Личное приложение на одном ПК и минимальная проверка

- **Статус:** `accepted`
- **Принято владельцем:** 2026-08-30
- **Дата:** 2026-08-30
- **Решение:** Map создаётся только для владельца и его текущего Windows x64 ПК. Поддержка чистой
  Windows, других компьютеров и отсутствующего runtime не требуется. Stage 11 как
  performance/packaging/release-candidate программа отменён.
- **Сборка:** обычный production build — framework-dependent `win-x64`; solution по умолчанию
  содержит только `src`. Tests запускаются адресно и не входят в обычную сборку.
- **Проверка:** один Release build; при реальном риске один относящийся test-project/filter; для
  UI один локальный smoke. Full-suite, отдельная независимая приёмка, pre-commit, coverage,
  mutation, benchmark, SBOM, VM, installer, signing и portable package выполняются только по
  новому прямому запросу владельца.
- **Очистка:** generated `bin/obj/artifacts`, исторические acceptance/workflow-материалы и
  неиспользуемые dev-инструменты не хранятся как часть приложения.
- **Supersedes:** требования DEC-007 о матрице первой поставки; Windows x64 как фактическая
  платформа сохраняется, но отдельной поставки и совместимости с другими ПК нет.

## DEC-017 — Непрерывная линия после Stage 11 и новая нумерация остатка

- **Статус:** `accepted`
- **Принято владельцем:** 2026-08-31
- **Дата:** 2026-08-31
- **Проблема:** отложенные функции исторически назывались 9B–9E, хотя линейная продуктовая история
  уже прошла Stage 10 и Stage 11. Запуск новой ветки с именем 9B и от Stage 10F создавал ложное
  впечатление отката и фактически отбрасывал более поздние commits.
- **Решение по Git:** новая функция начинается от последнего принятого product HEAD, указанного в
  `docs/STATE_HANDOFF.md`. На момент решения это
  `2c0a698e15573badb22a54de7ff1687ab784a9b2`. Старый грязный checkout может быть источником
  документационной/сборочной уборки, но не заменяет позднюю продуктовую базу.
- **Решение по Stage 11:** отмена VM/packaging/release scope не удаляет полезный production-код.
  Иконка, test-profile isolation и любые другие полезные изменения сохраняются; удаляется только
  ненужная процессная и релизная обвязка.
- **Новая нумерация:** бывший 9B становится Stage 12A (named checkpoints), 9C — Stage 12B
  (resize/crop/new-from-region), 9D — Stage 12C (full export/cancel), 9E — Stage 12D
  (migrations/corrupted-file diagnostics). Новые ветки и промты не используют номера 9B–9E.
- **GitHub:** будущий remote/repository/Project не определяет product HEAD и не является источником
  истины. Внешняя связка создаётся только по прямому разрешению владельца; до этого локальная
  разработка продолжается без блокировки.
