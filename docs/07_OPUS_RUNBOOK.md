# 07. Runbook для Claude Code Opus

## Разделение ответственности

| Роль | Обязанность |
|---|---|
| Владелец | принимает продуктовые, визуальные, лицензионные и рискованные решения |
| ChatGPT / Codex | формулирует один срез, фиксирует scope, проверяет изменения и пользовательский результат |
| Claude Code Opus | реализует только выданный срез, пишет/запускает проверки, честно сообщает ограничения |

## Один рабочий цикл

1. Тимлид читает фактическое состояние и выбирает один незакрытый срез.
2. Тимлид создаёт/обновляет один prompt-файл по шаблону ниже.
3. Opus сначала читает обязательные документы и возвращает короткий план.
4. Opus вносит небольшие изменения, проверяя каждый логический блок.
5. Opus запускает указанные сборки/тесты/smoke и возвращает доказательства.
6. После свежего self-check Opus создаёт один commit среза, сообщает base/head hash и останавливается.
7. Тимлид независимо читает точный `BASE..HEAD`, пересчитывает файлы, запускает ключевые проверки и смотрит настоящее окно/артефакт.
8. Исправления идут отдельным ограниченным prompt и новым commit, не вперемешку с ревью и без `--amend`.
9. Тимлид повторяет полный gate этапа на новом `HEAD`.
10. Только после gate обновляются handoff и статус этапа.

Полная матрица инструментов, adversarial-сценариев и Git-гейтов находится в `docs/11_CLAUDE_VERIFICATION_PROTOCOL.md`.

## Обязательная структура задания

```markdown
# Stage N — короткое имя

## Контекст
Фактическое состояние, принятые DEC и точка входа.

## Единственная цель
Один наблюдаемый результат.

## In scope
Закрытый список функций и разрешённых директорий/файлов.

## Out of scope
Явно запрещённые соседние улучшения.

## Инварианты
То, что нельзя сломать или обойти.

## Acceptance criteria
Нумерованный проверяемый список.

## Required verification
Точные команды, ручные сценарии, benchmark/golden/fault tests.

## Required report
Изменённые файлы, доказательства, PARTIAL/BLOCKED, риски, следующий шаг.
```

## Правила для Opus

- Не начинать код до чтения `AGENTS.md`, `STATE_HANDOFF` и задания.
- Не менять задачу на «сделаю всю архитектуру сразу».
- Не устанавливать пакет без проверки официального источника, лицензии, актуальной версии и нужды этапа.
- Не генерировать production assets и не скачивать чужие packs.
- Не добавлять облачный backend, аккаунт, telemetry или auto-update без принятого решения.
- Не скрывать ошибку try/catch с пустым обработчиком и не заменять реальное сохранение фальшивым success state.
- Не снижать acceptance ради зелёной сборки.
- Не удалять пользовательские файлы и не переписывать Git history.

## Формат итогового отчёта Opus

```markdown
## RESULT
Одно предложение о реально работающем результате.

## CHANGED
- путь — назначение изменения

## VERIFIED
- команда/сценарий — фактический результат и ключевые числа

## MANUAL UI CHECK
- шаги в настоящем окне и наблюдаемый результат

## PARTIAL / BLOCKED
- что не доказано и почему

## RISKS
- конкретный риск, без общих слов

## SCOPE CHECK
- подтверждение, что out-of-scope не менялся

## NEXT
- один рекомендуемый следующий срез, не выполненный самовольно
```

## Независимое ревью тимлида

Тимлид не принимает саморекламу отчёта как доказательство. Минимум:

- посмотреть `git diff --stat` и полный diff изменённых файлов;
- сверить зависимости и лицензии;
- запустить наиболее рискованные тесты отдельно;
- выполнить happy path и один failure path;
- проверить созданный `.mapproj`/export, а не только UI уведомление;
- убедиться, что out-of-scope файлы не изменились;
- отметить stale/непроверенное как `PARTIAL`.

Дополнительно обязательны полный список и число `A/M/D/R` файлов, чистый worktree, проверка solution/project references, локальных ссылок, package audit и доказательства того, что тест действительно ловит исходную ошибку. Общий зелёный статус test runner без проверки риска этапа не принимается.

## Когда остановиться и спросить владельца

- выбор меняет DEC, формат файла или поддерживаемую ОС;
- нужна платная лицензия, внешний аккаунт или коммерческий сертификат;
- предлагается чужой asset/code/design с неясными правами;
- исправление требует удалить/мигрировать реальные файлы пользователя;
- performance gate не проходит и требуется смена стека;
- два разумных варианта заметно меняют UX.

## Контекст между сессиями

`STATE_HANDOFF.md` содержит только проверенные факты, текущий scope, точные версии/команды, открытые риски и следующий шаг. Не переносить в него длинные рассуждения и планы, которые не приняты.
