# Полный аудит Map и сравнение редакторов карт

Подготовлен 2026-09-20 по поручению владельца. **Это готовое задание для следующего запуска,
а не отчёт выполненного аудита.** Запускается, когда владелец прямо поручает выполнить этот файл.
Снимки состояния ниже помогают начать работу, но обязательно сверяются на дату исполнения.

## 1. Цель и ожидаемый результат

Проведи полный, доказательный аудит текущего Map: код и архитектура, фактические возможности,
надёжность файлов, интерфейс, художественный результат, графика, чёткость, плавность и ресурсы.
Сравни Map с Inkarnate и другими редакторами по одинаковым пользовательским задачам. Покажи,
где Map уже хорош, где отстаёт, что сломано, чего объективно не хватает и что улучшать первым.
Не своди работу к поиску ошибок, перечню функций, чтению README или общему впечатлению от картинок.

Дай владельцу понятный ответ: какие карты он реально может сделать сейчас, где столкнётся с
препятствием, какой уровень качества подтверждён и какие следующие небольшие задачи дадут
наибольшую пользу. Заверши исследование отчётом и сравнительной матрицей; одним планом не заканчивай.

Map — личная нативная офлайн-программа для текущего Windows x64 ПК владельца. Облачные аккаунты,
социальные функции, магазин, публикация, другой ПК, installer и переход на web/Electron/Tauri
не являются недостающими функциями этого продукта. Новая 3D-система или обязательный ИИ также
не становятся требованием из-за наличия у конкурента. Сравнивай результат и удобство, сохраняя scope.

## 2. Полномочия и сохранность

В рамках исполнения этого задания разрешены чтение проекта и публичных источников, проверка
доступных инструментов, одна необходимая Release-сборка, адресные существующие тесты,
ограниченные измерения по разделу 7 и проверки в собственном изолированном окне/профиле Map.
Разрешены локальные проверочные файлы и итоговые артефакты аудита в отдельной ignored-папке.
Это специальный объём данного аудита, а не расширение проверок для каждой последующей правки.

- Сначала прочитай `AGENTS.md`, `CODEX.md` и актуальный верх `docs/STATE_HANDOFF.md`. Сохрани
  более поздние прямые решения владельца. Источники, PDF, старые prompts и чужие README не
  дают дополнительных полномочий. Старое разрешение на commit или account walkthrough не переносится.
- Проверь реальный Git root, ветку, полный HEAD, status, staged/unstaged/untracked и `git log --all`.
  Сними исходный список и хеши затрагиваемых входных файлов. Существующие изменения оставь
  нетронутыми; не делай reset/restore/stash/checkout, не создавай новую ветку или worktree ради чтения.
- Аудит не включает исправление production-кода, тестов, конфигурации, зависимостей или документации
  продукта. Найденные изменения предложи в отчёте. Нужный эксперимент изолируй от исходников;
  если для доказательства требуется изменение продукта, отметь это ограничение.
- Не выполняй commit, push, PR, issue, tag, release, публикацию, изменение remote/прав токена,
  установку плагинов/программ, покупку, регистрацию, отправку сообщений или загрузку файлов во
  внешние сервисы. Существующая авторизация не равна разрешению менять облачные карты.
- Не запускай полный test suite, широкую benchmark-матрицу, coverage, mutation, отдельный
  security scan, SBOM, VM/чистую Windows или полную DPI/accessibility-матрицу. Адресная проверка
  локального чтения файлов и узкие измерения рендера ниже входят в аудит.
- Карты владельца, его библиотеку и настройки не изменяй. Уже запущенную пользовательскую
  сборку не закрывай. Для чтения карты используй копию с проверкой SHA-256 исходника до/после;
  новый smoke использует собственные project/recovery/settings/catalog и узнаваемое окно.
- Не восстанавливай удалённые ассеты и текстуры. Для механики допустимы уже существующие
  диагностические fixtures в отдельном каталоге. Они не доказывают художественную готовность.
  Не импортируй их в рабочую библиотеку владельца.
- Краткий план не требует отдельного согласования. Выполняй независимые разрешённые части,
  пока ждёшь действительно нужных входных данных. Блокировка одного сайта не останавливает весь аудит.

  Ctrl+A в своём разделе, точный hit-test; невидимое не перехватывает ввод.
- Линии, фигуры, текст/кириллица/шрифты, заметки, сетки/snap, фильтры, композиции, версии,
  шаблоны, настройки, помощь и экспорт. Отложенные 21/22 учитывай как осознанную границу.
- Undo/Redo — завершённый жест равен одной транзакции, Esc не меняет файл/историю. Renderer не
  мутирует документ, Core не зависит от UI/Skia, dirty state и версии относятся к нужной revision.
- Save/autosave/recovery/backup: атомарность, согласованная миниатюра и revision, cancel/error,
  отказ по памяти/диску, copy-only migration, unknown/future schema и повреждённый файл.
  Chunked immutable edits не означают incremental ZIP-save: проверь фактическую полную запись.
- Чтение внешнего локального файла: лимиты ZIP/JSON/assets/raster, path traversal, decode bounds,
  linked paths, ошибка без потери исходника. Используй существующие малые fixtures/тесты;
  офлайн-продукт не освобождает от валидации данных, но это не поручение на отдельный security scan.
- Ресурсы: managed и native память, image sharing, bounded caches/eviction, GPU lifetime/thread
  ownership, cancellation/dispose, локальность invalidation, пространственный индекс и виртуализация.

Не называй отсутствие теста подтверждённой ошибкой. Найденный риск без воспроизведения пометь
как гипотезу; дай способ проверки. Учитывай, что тест может подтверждать адаптер или модель,
а не мышь/клавиатуру, файловый диалог и полный путь обычного пользователя.

## 6. Графика, чёткость и UX

Оцени отдельно: (1) интерфейс Blue Atlas/Onest; (2) корректность рендера; (3) качество исходного
арта; (4) композицию карты; (5) результат экспорта. Отсутствующий после DEC-037 арт — известный
контентный пробел. Оно не доказывает ни плохой renderer, ни хорошую готовую художественную сцену.

Сначала сохрани и сам просмотри реальные кадры. Для каждого: снимок кода/сборки, сцена/seed,
масштаб, viewport в физических px, DPI, режим покоя/движения/settle, путь к исходному изображению.
Проверочные crops сохраняй рядом с оригиналом и подписывай масштаб; исходник не ретушируй.
Синтетические fixtures прямо называй диагностическими. Не используй AI-картинки вместо результата Map.

Проверь на повторяемых сценах:

- 100% как оговорённое соответствие единиц карты экранным пикселям; отдельно Fit, дробное
  уменьшение, 400%, 800% и 1600%. Учти DPI, не сравнивай одинаковые подписи зума как одинаковое разрешение.
- Алиасинг, дрожание тонких линий, мыло, halo/alpha fringe, ступени mip, видимые границы тайлов,
  цвет/premultiplied alpha, clipping/bleed, качество текста и кириллицы, сетку и выделение.
- Совпадение preview/drag/idle/settled/save-reopen/export: материал и берег не исчезают при
  движении, сдвиге объекта, рисовании или отмене. Ускорение не оправдывает неверный порядок,
  пропажу объектов, разрушенную геометрию или подмену исходников низким разрешением в экспорте.
- Землю и воду разных уровней, прозрачный берег, приток под разными углами, очень широкое и
  узкое русло, ветвление дорог, острый поворот, замкнутый контур и окончания без игл/тёмных швов.
- Повторяемость узора, ритм колеи/обочины, читаемость силуэтов, масштаб и плотность объектов,
  сочетание толщин линий, света, теней, палитры и фактур. Вывод об арте делай только при его наличии.
- В UI: обнаруживаемость команд, активный инструмент/выделение, единицы и подписи, раскрытие
  сложных настроек, свободное место холста, прокрутку и footer действий, пустые/ошибочные/занятые
  состояния, обратную связь о памяти и долгой операции. Проверяй реальные состояния на текущем ПК.

Полная accessibility/DPI-сертификация не требуется. Можно отметить конкретную проблему focus,
контраста, подписи или обрезания на проверенном экране, не объявляя полное соответствие WCAG.

Художественные замечания делай конкретными: место на кадре → видимый эффект → почему мешает
карте → принцип улучшения → способ проверить. Вкус владельца и технический дефект разделяй;
художественную приёмку за владельца не объявляй.

## 7. Ограниченный протокол производительности

Сначала прочитай `tools/Map.Performance/README.md` и исходники выбранных профилей. Проверь,
что они измеряют и какие входы используют. `native-empty-artwork` проверяет пустую библиотеку,
но не доказывает FPS. `native-zoom-assets` по умолчанию читает действующий каталог, который после
DEC-037 пуст: не запускай его вслепую. При подходящих fixtures используй отдельный каталог через
`MAP_ZOOM_ASSETS_LIBRARY` и выбор сцен `MAP_ZOOM_ASSETS_SCENES`; переменные действуют только
в процессе проверки. `MAP_MEASURE_GPU_FLUSH=1` трактуй по коду, не как замер физического монитора.
Профили с удалёнными Mountains/материалами требуют пересмотра входов; не восстанавливай пакеты
и не запускай команды `install-*`. Старый `gatePassed` нельзя переносить на заменённую сцену.

Минимальный набор покрытий, без полного декартова произведения параметров:

| Сцена | Что доказать |
|---|---|
| S0: пустой профиль и маленькая цветная карта | Запуск/открытие, пустые каталоги, базовая отзывчивость, память простоя |
| S1: обычная 1920×1080, 1/10/100 штампов | Один большой исходник против многих, повтор одного SHA против разных SHA, pan/zoom/ghost/select |
| S2: смешанная рабочая карта | Земля, краска, мягкий берег, реки, дороги, текст, сетка и 40–100 штампов; правильный кадр во всех фазах действия |
| S3: 50 000 редактируемых объектов | Пространственный поиск, selection/one-object edit, виртуализация списка, стоимость локального изменения |
| S4: 100 000 объектов, разреженно и плотный участок | Граница деградации, холодный/тёплый вид, LOD, кэш, память; stress не равен обычной карте |
| S5: 131072², ограниченное число участков земли и до 20 000 объектов | Большой логический холст без full-canvas bitmap; размер и процент заполнения явно указаны |

S3–S5 выполняй последовательно после оценки доступной памяти и диска. Выбери минимальное число
существующих профилей, покрывающее эти вопросы. Если текущие средства не воспроизводят нужную
сцену без изменения продукта или превышают разумные ресурсы ПК, укажи NOT CHECKED и точный
недостающий эксперимент. Не подменяй её маленькой сценой с прежней большой подписью.
Не создавай полностью закрашенный максимальный холст или гигантский PNG ради формального рекорда.

Запиши CPU/GPU/RAM, свободную память, ОС, runtime/backend, размер окна и фактического canvas,
DPI/refresh rate (если доступен), сборку, fixture hash, seed, число видимых и всех объектов,
тайлы/слои/эффекты, размер/уникальность исходников. Чужие процессы не закрывай ради улучшения цифр.
Пустой, разреженный и плотно заполненный холст — разные нагрузки.

Для обычной и смешанной сцены используй один сценарий pan → zoom-in/out → select/drag → brush
→ idle/settle. Отдельно зафиксируй первый холодный проход, затем один прогрев и до трёх одинаковых
коротких измеряемых проходов. Длительность и число кадров задай до запуска; не продолжай повторять
до красивого результата. Для stress достаточно одного адресного прохода, повтор — при конкретной
неоднозначности. Если runner имеет другой протокол, опиши его фактические параметры и ограничения.

Измеряй отдельно:

- frame time P50/P95/P99, максимум, sample count, пропуски/паузы >50 и >100 ms, разброс между
  проходами. При слишком малой выборке не выдавай P99 за устойчивую оценку;
- CPU scene pass, GPU submission/ожидание flush, очередь UI, input-to-revision, первый видимый
  кадр и время уточнения после остановки. Укажи начало/конец каждого таймера;
- холодный первый кадр и уже готовый кэш, текущую точность рельефа и время полного settle;
- managed heap, process private/working set, доступную RAM и известные native/GPU allocations;
  не называй только GC-heap всей памятью приложения и не объявляй рост утечкой по одной точке;
- запуск, open/save/reopen, Undo/Redo, переключение инструмента и bounded export/cancel.
  Отдельно фиксируй сохранность документа и исходника при отказе/отмене.

Средний FPS за маршрут не скрывает медленный первый кадр. `1000 / P95(frame ms)` можно назвать
эквивалентом по времени кадра, но не средним FPS. Время off-screen Avalonia/Skia и GPU finish не
равно input-to-photon/scan-out физического монитора. Если физический путь не измерялся — так и напиши.

Историческая подсказка DEC-036, не текущий результат: обычные/умеренные сцены были выше 40 FPS,
100K zoom около 30–33 FPS, максимальная разреженная сцена имела overview около 25 FPS;
уточнение рельефа занимало примерно 3,8–4,1 s, встречался холодный кадр около 0,55 s.
Это разные метрики и старые входы до DEC-037. Первоначальную цель 60 FPS и позднюю 40+ сверяй
с конкретным принятым сценарием; не меняй acceptance задним числом.

### Сборка и адресная проверка

Из продуктового корня при необходимости свежего runtime выполни один раз:

```powershell
dotnet build .\Map.slnx -c Release -m:1 -nr:false -p:UseSharedCompilation=false
```

Используй существующие `bin/obj`. Утилита производительности — отдельная сборка только если
она нужна; проверь соответствие её DLL текущим исходникам. Не запускай обычный Map в профиле
владельца ради аудита. Если output занят пользовательским процессом, один отдельный выход
допустим без закрытия его окна; отметь, что именно запущено.

Выбирай тесты по риску: `Stage20RoadAudit*`, `Stage19LandSelectionTests`, `SoftLandRiverMouthTests`,
`EmptyAssetLibraryTests`, `LandMaterialWorkflowTests`, `RenderImageCacheTests`,
`StampSamplingRegressionTests`, `StreamingPngExportTests`, relevant round-trip/read-budget tests.
Сначала проверь актуальные имена/атрибуты и fixture-зависимости. Запускай нужный `.csproj` с
фильтром; не весь каталог. Укажи pass/fail/skip, число тестов и точную причину выбора.
Прочитанный тест не равен выполненному; зелёный тест не равен пройденному пользовательскому пути.

выбрать вопросы, но не являются свежей характеристикой конкурентов. Ниже стартовые источники,
а не полный набор доказательств. Проверь версию, платформу, тариф и дату конкретного утверждения.

Для первых четырёх составь отдельный детальный разбор; для остальных заполни ту же матрицу
релевантных измерений и объясни сильную сторону, компромисс и полезный для Map принцип.
Если источник не подтверждает функцию, ставь UNKNOWN/NOT CHECKED, а не «нет». Нерелевантное
измерение помечай N/A с причиной; отсутствие функции другого класса не снижает оценку автоматически.

Единые задания для сопоставления, только в применимых программах:

1. Регион: остров/берег, речная система с притоком и озером, дорога с развилкой, лес/горы,
   поселение, подписи; исправить форму после создания и экспортировать.
2. Поселение: дорога через воду/разные высоты, группы зданий/растительности, независимая правка
   ветви, читаемые перекрытия и сохранение редактируемости.
3. Небольшой battlemap/interior: сетка, стены/проём, поверхность, предметы, свет/тени и экспорт.
   Для Map явно отделить существующие универсальные средства от отложенных комнат/коридоров.
4. Поздняя правка: изменить геометрию/вариант/цвет, Undo/Redo, сохранить и открыть; оценить,
   насколько правка локальна и сколько действий требует. Не приписывай чужой внутренний алгоритм.

Сравнительные измерения: достижимость результата, число/сложность действий, обнаруживаемость,
редактируемость, связи объектов, precision/snap, графика, единообразие арта, качество текста,
масштабирование, лаги, ограничения памяти/экспорта, собственные ассеты, локальные файлы и offline.
Для облачных/коммерческих продуктов тарифные/аккаунтные ограничения — контекст, не запрос покупки.

В матрице каждой функции укажи для Map и аналога: результат, статус, уровень доказательства,
версия/тариф/дата, источник, ограничение сравнения и вывод для владельца. Уровни доказательства:
`LIVE` — реально пройдено в UI; `OFFICIAL` — заявлено разработчиком; `HISTORICAL` — старый
датированный walkthrough; `INFERENCE` — вывод с основанием; `UNKNOWN` — нет данных.
Статус реализации и уровень источника — разные столбцы.

Не объявляй Map быстрее по числу единиц холста или против демонстрационного ролика конкурента.
Численный FPS-рейтинг допустим только при сопоставимых версиях, аппаратуре, viewport, сцене,
эффектах и протоколе. Если этого нет, сравни возможности/наблюдаемое поведение, а скорости поставь
«несопоставимые измерения». Галерея опытного художника не равна результату новичка за один час.
Отдельно сопоставь исходный арт, выразительность инструментов и итоговую композицию.

Не закрепляй формулировку «Inkarnate только браузерный» по одному FAQ: в старом исследовании
есть упоминание desktop app. Проверь актуальные release notes и зависимость от сети отдельно
для каждой доступной версии; наличие desktop-клиента само по себе не доказывает offline.

### Работа на сайтах

Начни с официальной документации и публичных уроков. Для динамической страницы используй
доступный Browser tool, предварительно прочитав его API. Выбирай элементы по свежему наблюдению;
после навигации/изменения состояния обновляй снимок. Не угадывай controls и не используй скрытые
store/model/network API. В browser canvas ориентируйся на реальный кадр и проверяй результат.

Авторизованный редактор открывай только в пределах актуального разрешения. Без него можно
читать публичные источники и разрешённое демо; не создавать/клонировать/удалять облачные карты,
не менять рабочие проекты, не экспортировать чужие assets и не принимать новые договорные условия.
Если live-доступ закрыт, продолжай по официальным материалам и честно укажи пробел. Не запрашивай
пароли, cookies, tokens и 2FA; логин при необходимости выполняет сам владелец.

Сравнивай публично наблюдаемые действия и результат. Не копируй код, закрытые данные, ассеты,
названия пакетов или фирменное оформление Inkarnate; не выгружай сайт целиком. Для доказательства
достаточны ссылка, короткое описание и минимальный разрешённый снимок. Не пытайся обходить
ограничения сайта. Закрой только созданные тобой исследовательские вкладки, когда они уже не нужны.

## 9. Репозитории и документация для объяснения причин

Начинай с существующего решения Map. Для каждой подтверждённой проблемы сначала объясни причину,
потом предложи минимальный способ исправления. Внешний код — материал для изучения, а не готовое
разрешение добавить зависимость или перенести архитектуру.

| Источник | Какой конкретный вопрос помогает решить |
|---|---|
| https://github.com/AvaloniaUI/Avalonia и https://docs.avaloniaui.net/ | Layout/measure, виртуализация, render scheduling, UI thread и input; смотреть APIs установленной версии 12.1.1 |
| https://github.com/mono/SkiaSharp и https://skia.org/docs/ | Sampling/mip, alpha, filters, GPU context, resource ownership, atlas/batching; учитывать SkiaSharp 3.119.4 и его native Skia |

## 10. Выходные материалы и критерии завершения

Сохрани результат в одной новой папке `artifacts/audits/<дата-время>/` продуктового корня,
предварительно убедившись, что она игнорируется Git и не содержит чужих файлов. Не перезаписывай
прежний аудит. Обязательные файлы: `MAP_AUDIT_REPORT.md`, `COMPARISON_MATRIX.csv` (UTF-8).
Снимки и исходные JSON/CSV измерений храни только в нужном для выводов объёме рядом с отчётом.
Укажи абсолютные пути в финальном ответе. Отчёт должен читаться без этой переписки.

Структура отчёта:

1. Ответ владельцу: текущее состояние, реальные сильные стороны, основные препятствия и один
   рекомендуемый следующий шаг. Техническую готовность, художественное наполнение и удобство разделить.
2. Проверенный снимок и охват: branch/HEAD/dirty, сборка/среда, прочитанные материалы,
   реально выполненные проверки и их ограничения; отдельный список NOT CHECKED.
3. Функциональная карта и соответствие roadmap/решениям. Реестр расхождений документов с кодом
   с датой и приоритетным источником; не исправлять документы молча.
4. Находки по убыванию влияния. Каждая: ID, приоритет P0–P3, статус доказательства, подсистема,
   пользовательский ущерб, предусловия, шаги, ожидаемое/фактическое, file:line и/или screenshot/log,
   причина/уверенность, минимальное предложение и проверяемое условие исправления.
5. Графика/UX: реальные кадры и локальные замечания; отдельная оценка renderer и доступного арта.
6. Производительность: метод, входы, таблица и при необходимости график времени кадра/памяти;
   холодные/тёплые/settle результаты, выявленное узкое место и предел применимости каждого числа.
7. Подробное сравнение четырёх основных аналогов и остальных шести; матрица, источники,
   где Map лучше/сопоставим/хуже/пока несравним и почему. Не выдумывать оценки для пустых ячеек.
8. Статус старых F01–F10/A01–A09 и известных замечаний дорог/воды/рендера: новое доказательство,
   исправление/регрессия/непроверенность. Не считать дубликаты отдельными проблемами.
9. Предложения: сначала потеря данных/поломка рабочего пути, затем измеренные задержки и
   неверная графика, затем удобство и отдельный арт-план. По каждой задаче — польза, границы,
   файлы/зависимости, риск, оценка размера с оговоркой, критерий результата. Не начинать 21/22.
10. Что остаётся неизвестным и какой минимальный следующий эксперимент это разрешит.

Минимальные поля CSV: `program,scenario,dimension,map_result,other_result,map_status,
other_status,evidence_level,version_or_tier,checked_at,source,evidence_path,limitation,
conclusion_for_map`. Для больших текстовых полей используй корректное CSV-экранирование.
Числовые оценки 0–5 допустимы только при явной шкале и достаточных данных; общий балл не нужен.
Не превращай UNKNOWN/N/A в ноль. Важность критериев для личного Map объясни до ранжирования.

Готово, когда все заявленные направления разобраны, ключевые пользовательские сценарии имеют
прямое доказательство либо точную границу NOT CHECKED/BLOCKED, выводы о графике привязаны к
просмотренным кадрам, числа воспроизводимы, источники конкурентов датированы, найдены и сильные
стороны, и проблемы, а следующие задачи конкретны. Блокировки не скрыты общей фразой «аудит пройден».

Проверь согласованность отчёта и CSV, существование ссылок на файлы/снимки, выборочные расчёты
метрик и соответствие каждого серьёзного вывода доказательству. Сравни итоговые хеши/status с
исходными: продукт, пользовательские изменения, карты и библиотека должны остаться нетронутыми.
Не заявляй проверку, которую только подготовил, и не делай повторную независимую приёмку ради формы.

Финальный ответ на русском: сначала главный результат и ссылки, затем что проверено и что
ограничивает выводы. Заверши разделом `## ИТОГИ` по AGENTS.md: `Сделано`, `Что дальше`,
`Реализация проекта`. Процент — только оценка всей действующей roadmap с явным основанием,
не доля зелёных тестов и не процент этой задачи. При недостаточной основе напиши
«не подтверждена» с причиной; отсрочки и пустое художественное наполнение не делай готовыми.
